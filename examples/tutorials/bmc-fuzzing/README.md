# BMC Fuzzing: BIOS + OpenBMC in Simics

A feasibility example: fuzzing BMC firmware with TSFFS, in a Simics setup
where a platform BIOS and OpenBMC boot together, working toward fuzzing the
BIOS<->BMC interaction surface.

Everything here uses public sources only - the public X58I board from the
[edk2-simics-platform-bios tutorial](https://intel.github.io/tsffs/tutorials/edk2-simics-platform-bios/),
and [openbmc/openbmc](https://github.com/openbmc/openbmc) built for the
public `evb-ast2600` machine. No Intel-internal platform packages, BIOS
sources, or firmware images are used or required.

## Status

- [x] Boot public EDK2 BIOS (X58I board, per the [tsffs edk2-simics-platform-bios tutorial](https://intel.github.io/tsffs/tutorials/edk2-simics-platform-bios/)) - see `bios-x58i/`; required a few fixes beyond the tutorial (see below)
- [x] Harness the BIOS boot logo parser (LogoFAIL) with TSFFS, per the tutorial's own DxeLogoLib patch - validated end-to-end: snapshot/restore, testcase injection, and re-execution all confirmed working via repeated fuzzing runs
- [x] Boot real OpenBMC (built from [openbmc/openbmc](https://github.com/openbmc/openbmc) source) on an ASPEED AST2600 Simics model - see `openbmc-ast2600/`; boots cleanly through kernel init, systemd, and all phosphor D-Bus services to the `login:` prompt; required two kernel-side fixes for this Simics target (see below)
- [x] Boot both together in one Simics session (no interconnect wiring yet - side-by-side boot only) - see `scripts/combined-boot.simics`; BIOS reaches its boot menu and BMC reaches its `login:` prompt concurrently in the same session
- [x] Harness OpenBMC's libpldm firmware-update decoder with TSFFS - see `openbmc-ast2600/harness-libpldm/`; compiled-in (not closed-box - see docs), running bare-metal on the AST2600 model, no OpenBMC boot required
- [x] Run a fuzzing campaign against the harnessed decoder, confirm crash detection - a 10-minute campaign found 20 distinct crash signatures; see `docs/libpldm-fuzzing.md` for detail and an open repro-mismatch caveat that still needs chasing down
- [ ] (Future work, not covered here) Wire a real interconnect (LPC/KCS or eSPI, platform-dependent) between the two boots so BIOS-originated input can reach the BMC target

## Structure

- `bios-x58i/` - EDK2/X58I BIOS build (public sources, Docker build per upstream tutorial)
  - `Dockerfile`, `build.sh`, `tsffs.h` - build the LogoFAIL-harnessed `BOARDX58ICH10.fd`
  - `project/` - Simics project (targets, `run.simics`, `fuzz.simics`, `corpus/`)
- `openbmc-ast2600/` - OpenBMC build (public source, `evb-ast2600` machine)
  - `Dockerfile`, `build.sh`, `linux-aspeed_%.bbappend` - build the `image-bmc` flash image
  - `scripts/boot.simics` - boots the built image on a user-supplied AST2600 model
  - `project/deploy/` - build output (gitignored; regenerated by `build.sh`)
- `openbmc-ast2600/harness-libpldm/` - TSFFS harness for libpldm's firmware-update decoder (bare-metal ARM32, compiled-in)
- `scripts/combined-boot.simics` - boots the X58I BIOS and OpenBMC together in one Simics session (no interconnect wired yet)
- `scripts/fuzz-libpldm.simics` - runs the libpldm firmware-update decoder fuzzing campaign
- `docs/libpldm-fuzzing.md` - write-up of the libpldm harnessing approach and campaign result

## BIOS build notes (fixes beyond the upstream tutorial)

The tutorial's documented commit pair (`edk2`@eccdab6, `edk2-platforms`@f446fff) fails
a shallow submodule clone at this point in time; `intel/tsffs`'s own maintained example
Dockerfile bumps to `edk2`@edk2-stable202505 / `edk2-platforms`@51c7f294 to work around
this (see [tsffs#168](https://github.com/intel/tsffs/pull/168)), which is what
`bios-x58i/Dockerfile` is based on. That newer pair has two further, unrelated bugs when
building `BoardX58Ich10X64` that needed working around here:

1. StandaloneMM's `MmIplBuildMmCoreModuleHob` asserts the loaded MmCore image size is
   page-aligned; it isn't for this board's binary, so the debug build hangs in PEI before
   reaching DXE. Relaxing that ASSERT alone then exposes a second bug (StandaloneMM's own
   FV-shadow allocator fails to load the DXE firmware volume) - pointing at a broken
   StandaloneMM stack for this board at this commit, unrelated to the LogoFAIL harness.
2. Fix: switch the board to the traditional (non-Standalone) PI SMM stack, which the
   board's own DSC/FDF already gate behind `PcdStandaloneMmEnable` as a working
   alternative. Traditional SMM's slightly larger module set then overflows
   `FVMAIN_COMPACT`'s fixed size budget by a small margin; fixed by shifting spare bytes
   from the adjacent SECFV region (temp-memory SEC/PEI FV) to FVMAIN_COMPACT, since the
   overall 2MB flash image is already packed against the 4GB boundary and can't grow.

With both fixes applied, the BIOS boots cleanly through SEC/PEI/DXE/BDS to the boot menu,
and `fuzz.simics` (the upstream tutorial's harnessed-fuzzing script, paths adjusted here)
runs the TSFFS fuzzer against the LogoFAIL-harnessed `DxeLogoLib` target successfully -
confirmed via repeated `HARNESS_START`/`HARNESS_STOP` magic-instruction round-trips and
snapshot restores across fuzzing iterations.

## OpenBMC build notes (fixes for this Simics target)

`openbmc-ast2600/Dockerfile` clones `openbmc/openbmc` (machine `evb-ast2600`, the
board family the target AST2600 Simics model implements) and runs
`bitbake obmc-phosphor-image`. Out of the box this boots through u-boot but then hangs
before reaching userspace on this Simics target, for two unrelated reasons fixed via
`linux-aspeed_%.bbappend`:

1. The board devicetree overrides `uart5`'s (the console UART) `compatible` string from
   the generic `ns16550a` to `snps,dw-apb-uart` as an "A0 workaround". That driver probes
   Synopsys DesignWare-specific extended UART registers beyond the standard 16550
   register window, which the target Simics AST2600 model doesn't implement - an
   unmapped write there triggers a watchdog-driven full-SoC reset in a loop, before Linux
   ever prints a single line. Fix: drop the override via a `do_patch` postfunc, falling
   back to the plain `ns16550a` driver.
2. The BMC boot flash JEDEC-identifies as a Micron n25q512ax3 (64MB); the kernel's
   `micron-st.c` driver marks that chip `USE_FSR`, meaning it polls the Read Flag Status
   Register (opcode `0x70`) after every erase/write instead of the plain status register.
   The target Simics `generic_spi_flash_ext` model doesn't implement that opcode, so
   every JFFS2 rwfs write during boot spins forever polling an always-unimplemented
   register. Swapping to a same-size Winbond JEDEC ID (which doesn't use FSR at all) was
   tried first but broke u-boot's own SPI flash probe (`spi_flash_probe_bus_cs()`
   failed) - its detection depends on the ID/size pairing too, not just avoiding FSR.
   Fix instead drops just the `USE_FSR` flag for this specific chip ID in
   `drivers/mtd/spi-nor/micron-st.c`, keeping the Micron identity both u-boot and Linux
   already detect correctly. (Real n25q512ax3 hardware still benefits from FSR-based
   status polling, so this fix is scoped to the Simics target build only, not upstreamed.)

With both fixes applied, the built `image-bmc` boots cleanly through the kernel, mounts
both the squashfs rootfs and jffs2 rwfs, and brings up the full phosphor D-Bus service
mesh (inventory manager, sensor monitor, network manager, BMC/chassis/host state
managers, IPMI, MCTP, bmcweb, ...) to the `evb-ast2600 login:` prompt - validated via a
full boot run against `scripts/boot.simics`.

## Combined boot (BIOS + BMC, no interconnect yet)

`scripts/combined-boot.simics` loads both targets in one Simics session: the X58I
BIOS (`load-target "qsp-x86/qsp-uefi-custom"`) and OpenBMC
(`run-script "targets/ast2600/bmc.simics"`). Both boot fully and independently side
by side - the BIOS reaches its boot menu, OpenBMC reaches its `login:` prompt - but
nothing wires them together yet; that's future work (see Status above).

Two things needed adjusting relative to running each target alone:

- The BIOS firmware override had to go through `machine:software:firmware:bios`
  rather than `machine:hardware:firmware:bios` (the path used in
  `bios-x58i/project/run.simics`). Both resolve to the same underlying parameter -
  `hardware:...:bios` is defined as a `^machine:software:firmware:bios` reference in
  the target yml - but only the `software:` leaf reliably accepted an override when
  loaded alongside the BMC target in the same session.
- Needed a couple of Simics-7 packages beyond what either target alone required:
  Crypto-Engine (`qsp.mb.cpu0`'s AES support) and, depending on your own AST2600
  model's dependencies, packages like infra-tools/testingframework/arm-cpu/arm-juno/
  synopsys-dw. See the comment header in `scripts/combined-boot.simics`.

Run with `$repo_root` set to this directory's absolute path:

```sh
./simics -no-gui --no-win \
    -e '$repo_root = "/absolute/path/to/tsffs/examples/tutorials/bmc-fuzzing"' \
    /path/to/scripts/combined-boot.simics
```

## libpldm firmware-update decoder harness

`openbmc-ast2600/harness-libpldm/` harnesses
`decode_pldm_firmware_update_package()` (PLDM Type 5 firmware-update package
decoder) with TSFFS - the top pick from an earlier shortlist of fuzz targets
on the BIOS↔BMC interaction surface: a pure decode-a-buffer-into-a-struct
function, no grammar or authentication needed to reach it.

This uses a **compiled-in** harness rather than closed-box: rather than
booting the full OpenBMC image and finding pldmd's live socket-read call
site, the harness links libpldm's decoder source directly into a small
freestanding ARM32 ELF and runs it bare-metal on the target AST2600 model's
Cortex-A7 core, entirely bypassing OpenBMC boot. Full detail - including a
GCC NEON-codegen gotcha that made every single fuzzing iteration crash
identically until diagnosed, and the same ARM32 `HARNESS_START` upstream bug
fix as the BIOS side needed - is in `docs/libpldm-fuzzing.md`.

Build and run:

```sh
cd openbmc-ast2600/harness-libpldm && ./build.sh   # needs gcc-arm-linux-gnueabihf
./simics --batch-mode /path/to/scripts/fuzz-libpldm.simics
```

A 10-minute campaign against a fresh random corpus found 20 distinct crash
signatures (see `docs/libpldm-fuzzing.md` for the full result and an open
caveat: `@tsffs.iface.fuzz.repro()` did not reproduce at least one signature
tested standalone after the campaign, which needs chasing down before
root-causing any of them).

## Model dependency

The ASPEED AST2600 Simics model is **not included** and is not publicly distributable.
Scripts expect it as a pre-installed Simics package on the user's own system; the model
path is parameterized, not bundled. Both authors (Intel, Oracle) have separate access
to this model or an equivalent BMC model through their own channels.

## Related fixes upstream in tsffs

Getting the libpldm harness above working correctly on ARM32 surfaced a bug
in `harness/tsffs-gcc-arm32.h`: `HARNESS_START` and its variants were missing
the `DEFAULT_INDEX` argument that every other architecture's harness header
passes, which meant the start harness was silently never recognized. That's
fixed directly in this repo's `harness/tsffs-gcc-arm32.h` now; see its git
history, and
[Bare-Metal and Non-x86 Compiled-In Harnessing](../../../docs/src/harnessing/bare-metal.md)
for the general technique this example uses.
